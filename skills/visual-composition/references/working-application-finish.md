# Working application finish

Read for new or substantially changed dashboards, settings, editors, administration, and other working applications. Apply only to the changed surface. Preserve explicit user choices, existing product contracts, and brand requirements; this is not a universal style for marketing or editorial pages.

## Operate: compose around the next task

- Identify what the user needs to see or do next. Give that task useful space and direct access; do not place it below a promotional introduction or a large inventory merely to balance the layout.
- Default to a descriptive title with necessary actions. Add scope, status, or instructions only when they change interpretation or enable a decision. An established workspace indicator or meaningful workflow step can remain necessary context.
- Prefer familiar controls, readable working typography, and density suited to scanning and input. A new visual signature is optional; consistent behavior across screens is essential.
- Make action, selection, focus, pending, and error roles recognizable across components. Keep emphasis proportional to importance; inactive chrome should not compete with the task.
- Specify the whole component surface: a picker includes its opened list, a menu its items, and a dialog its content and return path. Reuse the existing component vocabulary rather than designing only the closed frame.

## Distill: remove without losing meaning

After the structure and relevant states exist, assess the changed region as a whole:

- For supporting text, badges, and decorative containers, ask what information or operation would be lost by removal. Remove repeated explanations, self-evident instructions, slogans, ornamental numbering, and wrappers that contribute no useful grouping.
- Do not move redundant copy into a tooltip or invent replacement copy to preserve a layout slot. Reflow the freed space toward the task.
- Preserve persistent labels, accessible names, current scope, units, consequences, actionable errors, and honest limits of the displayed data. Simplification must not conceal uncertainty or make users remember essential context.
- Consolidate repeated notices only when the remaining notice is visible at the relevant decision. Do not remove a necessary local warning because a similar message exists elsewhere.
- Preserve supplied content requirements and established navigation. Removing features, changing workflow, or collapsing necessary context is not a copy cleanup.

## Polish: finish the user path

For implementation, inspect the rendered changed path with realistic content at representative supported widths; for design, specify these states in the handoff; for review, report only observed or supplied evidence.

- Address broken behavior, misleading data, and access barriers before missing states, layout inconsistencies, and cosmetic refinements. Retain the chosen visual direction rather than introducing a late redesign.
- Open the controls and inspect their full surfaces: typography, spacing, state colors, boundaries, scrolling, and positioning must fit the surrounding interface. Check focus and selection together, disabled content, long labels, and viewport-edge behavior where applicable.
- Walk the affected path through action, pending/result or recovery, dismissal, and continued work. Verify applicable pointer and keyboard behavior; add touch checks for supported touch layouts. A closed screenshot cannot establish this coverage.
- Batch discovered fixes, then recheck affected states. Stop when scoped acceptance criteria pass; expand checks only for a new failure or unresolved risk. If a required state cannot be inspected, identify it as unverified rather than declaring completion.
- Assess explicit acceptance criteria individually. Successful functional tests do not offset a visual requirement violation, and visual polish does not offset broken interaction. Report material failures and unverified states separately from subjective preferences.
